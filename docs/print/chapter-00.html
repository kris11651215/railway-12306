0.1 为什么先学铁路业务

12306 难，不在于"增删改查"，而在于业务规则复杂：

  • 一个座位可以卖给多个人，只要乘车站段不重叠（席位复用）；
  • 票不是随便卖的，始发站和中间站有配额（票额分配）；
  • 票价不是简单的"单价 × 里程"，长途每公里更便宜（递远递减）；
  • 你买不到直达票，系统还得帮你拼换乘（路径规划）。

如果不理解这些规则，写出来的余票查询 SQL 一定是错的。所以本章先把业务地图画出来，第1章之后再用代码一层层实现。

0.2 铁路业务常识

0.2.1 车次字母：一张表看懂列车等级

字母含义速度等级特点
G高速动车组最高时速 300-350km/h，高铁主力
D动车组中高时速 200-250km/h，部分走既有线
C城际动车组中高城市群之间高频短途，如广深城际
Z直达特快普速最快停站极少，多为夕发朝至
T特快普速较快停大站，速度次于 Z
K快速普速常规停站较多，覆盖广
（无字母）普客/普快普速最慢站站停，价格最低

记忆要点：字母代表等级，等级决定路网优先级。等级越高，调度越优先，晚点时越容易被"保"。

对项目的影响：车次表 train 需要 train_type 字段；排序时 G > D > C > Z > T > K；抢票模块对不同等级车次的热度不同。

0.2.2 上下行：车次单双数的由来

  • 上行：开往北京方向（或支线开往干线方向），车次用双数，如 G100、K234。
  • 下行：离开北京方向（或干线开往支线方向），车次用单数，如 G101、K235。

同一趟车在途中若改变方向，车次会"变号"。例如某些列车在某站停靠后由上行变下行，车次从 G100 变为 G101。

对项目的影响：路径规划时不能只看车次号，要结合经停站顺序与方向；数据建模时 train_station 表需要 station_order（站序）字段。

0.2.3 席位复用与余票裂变（本章最核心）

这是铁路票务区别于普通电商库存的根本所在。

假设一列 G100 从北京西开往广州南，中途停靠：石家庄、郑州东、武汉、长沙南。一个座位在整条线路上可以拆成多个区段售卖：

北京西 —— 石家庄 —— 郑州东 —— 武汉 —— 长沙南 —— 广州南
   A段      B段       C段      D段      E段
  • 乘客甲买了 北京西 → 郑州东（A+B 段）；
  • 此时 郑州东 → 武汉、武汉 → 长沙南、长沙南 → 广州南 仍然可以继续卖；
  • 乘客乙再买 郑州东 → 长沙南，座位就从郑州东开始被乙占用；
  • 只有当某个区段被占满时，该区段才真正"无票"。

所以：

  • 余票 ≠ 总座位数 − 已售张数，而是按区段分别计算：某区段余票 = 该区段未被任何乘客占用的座位数。
  • 一个座位从"一整条"变成"一串可售区段"，仿佛裂变成多张票——这就是余票裂变。
  • 查询"郑州东 → 武汉 有票吗"，本质是问：有没有一个座位的占用区间覆盖了郑州东到武汉这一段。

对项目的影响（贯穿全项目）：

  1. seat_inventory 表必须按 车次 + 日期 + 座位类型 + 起始站序 + 终止站序 记录余票；
  2. 扣减库存时要判断区段重叠，不能简单 stock - 1；
  3. 高并发抢票（第4章）的防超卖难点，正是在"多区段库存一致性"上。

0.2.4 票额分配原则：长途优先，兼顾中短途

铁路不是"谁先买谁得"，而是有计划的票额投放：

  • 初期大部分票额分配给始发站，优先保障长途旅客（长途旅客选择少，短途旅客有替代方式）；
  • 中间站只拿到少量票额，保证短途也有票可买；
  • 临近发车或长途票未售完时，票额会动态释放给中间站；
  • 还有"共用票额"机制：一段区间内的票额可被多个站共享使用。

对项目的影响：候补分析（第6章）要能识别"长途有票、短途候补积压"的情况，给出长途票额调配短途和动态加开建议——这正是广铁长沙南实践的核心逻辑。

0.2.5 票价递远递减

票价不是简单的"每公里单价 × 里程"，而是里程越长，平均每公里运价率越低：

里程区间平均每公里运价特征
短途（如 0-200km）单价高
中途（如 200-1000km）递减
长途（1000km 以上）单价最低

所以"北京 → 上海"的票价，小于"北京 → 南京"+"南京 → 上海"两段票价之和。

对项目的影响：第5章"最经济换乘"策略不能把分段票价简单相加，要按递远递减规则计算，否则会算出一条"绕路但总价看起来便宜"的假最优路线。

0.2.6 同车接续

直达票卖完了，但同一趟车"北京 → 郑州"和"郑州 → 武汉"都还有票，可以分段买同一趟车，中途不下车（可能换座位），这叫同车接续。

  • 与换乘不同：同车接续不需要换车，只是换席位；
  • 是候补/购票助手推荐的重要兜底方案；
  • 实现上：对同一 train_id 检查两段库存都有余即可组合。

对项目的影响：第5章换乘路径的候选集中，应包含"同车接续"这类路径；第6章 AI 购票助手可以用自然语言提示"可分两段买同一趟车"。

0.2.7 路网格局：八纵八横与三横五纵

八纵八横是高铁主通道（2016 年《中长期铁路网规划》）：

  • 八纵：沿海、京沪、京港（台）、京哈—京港澳、呼南、包（银）海、兰（西）广、京昆；
  • 八横：绥满、京兰、青银、陆桥、沿江、沪昆、厦渝、广昆。

三横五纵是对普速干线东西、南北通道的通俗概括：常见的纵向五大通道如京沪、京广、京九、京哈、焦柳，横向三大通道如京包—包兰、陇海—兰新（陆桥）、沪昆（不同资料口径略有差异）。它与高铁网共同构成"普速保覆盖、高铁保效率"的双层路网。

对项目的影响：路径规划的数据不是"任意两站随便连"，而是沿真实线路的图结构；枢纽站是图中的高连接度节点，换乘大概率发生在枢纽。

0.2.9 系统架构常识：从 12306 看分布式系统

概念通俗解释对项目的启发
混合云架构核心票务跑私有云（安全、稳定），查询与营销类弹性业务跑公有云（削峰、省钱）我们的项目规模小，但要有"读写分离、缓存抗查询压力"的意识
最终一致性不追求每一刻全系统完全一致，允许短暂不一致，但最终一致余票查询走缓存，下单以数据库扣减为准，两者允许短暂偏差
WAL 事务日志先写日志再改数据（Write-Ahead Log），崩溃后可按日志恢复MySQL 的 redo log 就是 WAL；第2章事务专题重点
余票扣减写扩散买一段票，可能影响多个区段余票记录，写操作被放大第4章高并发优化的核心难点之一
支付与库存一致性支付成功但库存没扣、或超时未支付库存没释放，都会出问题用"预扣库存 + 超时释放 + 对账"保证最终一致

0.4 环境搭建

0.4.1 JDK 17

  • 项目要求：JDK 17（LTS），Spring Boot 3.x 的最低要求也是 17；
  • 下载：Eclipse Temurin 17（或 Oracle JDK 17、Microsoft OpenJDK 17）；
  • 安装后配置环境变量 JAVA_HOME 指向 JDK 目录，并把 %JAVA_HOME%\bin 加入 Path；
  • 验证：
java -version
# 期望看到 17.x 输出

说明：本机已安装 JDK 21，Spring Boot 3.x 在 21 上也能运行。项目 pom 中设置 <java.version>17</java.version>，以确保代码兼容 17。生产/面试演示建议统一用 17。

0.4.2 Maven

Maven 是 Java 的依赖管理与构建工具，本章只需要 L2 会用。

  • 下载：Apache Maven 3.9.x 二进制 zip；
  • 解压到无中文、无空格的路径，如 D:\tools\apache-maven-3.9.x；
  • 配置 MAVEN_HOME，并把 %MAVEN_HOME%\bin 加入 Path；
  • 国内加速：在 ~/.m2/settings.xml 配置阿里云镜像：
<mirrors>
  <mirror>
    <id>aliyun</id>
    <mirrorOf>central</mirrorOf>
    <name>aliyun central</name>
    <url>https://maven.aliyun.com/repository/public</url>
  </mirror>
</mirrors>
  • 验证：
mvn -v

0.5.5 依赖冲突：排查与解决

  • 成因：A 依赖 X-1.0，B 依赖 X-2.0，Maven 只能选一个版本；
  • 选取规则：最短路径优先；路径相同时先声明者优先；
  • 排查：mvn dependency:tree -Dincludes=groupId:artifactId；
  • 解决：<exclusions> 排除传递依赖，或在本工程显式声明想要的高版本。

0.5.6 profile 切换

<profiles>
  <profile>
    <id>dev</id>
    <activation><activeByDefault>true</activeByDefault></activation>
    <properties><env.name>dev</env.name></properties>
  </profile>
  <profile>
    <id>prod</id>
    <properties><env.name>prod</env.name></properties>
  </profile>
</profiles>

打包时用 -Pprod 激活不同环境配置，避免手动改配置。

0.7 自检三问（能答即过关）

以"席位复用"为例：

  1. 是什么：一个座位的运输能力按区段拆分，多乘客可复用同一座位；
  2. 为什么：提高座位利用率，让区间票也能卖出；
  3. 怎么排错：若余票计算错误，先查 seat_inventory 的区段起止站序是否重叠判断正确，再用 EXPLAIN 看查询是否走索引。
